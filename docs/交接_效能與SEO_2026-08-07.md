## 一、P1 字體瘦身：徹底跳出 next/font（工單方案 A ＋ B 一次做齊）

### 診斷確認

工單量到嘅數字同上一輪本機診斷完全對得上：字體 2,167 KB 佔全站傳輸 88%，
536 條 `@font-face` 塞喺 3 個渲染阻塞 CSS 檔（595 KB 未壓縮／89 KB 壓縮）。
TBT 0 ms、CLS 0，即係話問題純粹係字節數，同 JS 執行同版面無關。

### 做法

1. **內文（Noto Sans TC）整個移除**，改用系統 CJK 堆疊。
   iOS／macOS 落 PingFang TC、Windows 落微軟正黑、Android 本身就係 Noto Sans CJK，
   三邊觀感同原本幾乎一致，但省返 18 個檔／1,123 KB 同 211 條 `@font-face`。

2. **標題（Noto Serif TC）保留，但改自行 subset 自託管**（工單方案 B）。
   新增 `scripts/build_font_subset.py`，用 `fontTools` 由 `NotoSerifTC-VF.otf`
   切出 400／700／900 三個字重嘅精簡 woff2，放 `public/fonts/`，
   `@font-face` 寫喺自動生成嘅 `src/app/fonts.css`。

3. **兩層 subset，解決「日後加新標題會缺字」呢個方案 B 嘅已知風險**：

   | 層 | 字表來源 | 大小 | 幾時下載 |
   |---|---|---|---|
   | core | 掃 `.next` 產生嘅 225 個 HTML，抽所有 `font-serif` 範圍內實際算繪嘅字＋`.prose` 首段首字（朱批大字）＝222 字 | 每字重 ~62 KB | 正常情況只下載呢層 |
   | ext | 安全網：全部文章標題／Markdown 標題／`.tsx` UI 字串＝1,406 字 | 每字重 ~295 KB | `unicode-range` 圈住整個 CJK 區但排喺 core 之前，只有出現 core 冇涵蓋嘅字先會拉，平時零位元組 |

   CSS 後定義者優先，所以 core 有嘅字一定由 core 出，ext 唔會被拉。
   萬一連 ext 都冇（極罕），字型堆疊後面仲有系統宋體兜底，唔會出豆腐方格。

4. `preload` 只落首頁（首頁 LCP 元素＝hero H1，`font-serif font-black`＝900）。
   用 `react-dom` 的 `preload()` 而唔係喺 `<head>` 寫 `<link>`，因為 Next 會將 head 內嘅 link
   再 hoist 一次，會出兩條重複標籤。68 個詞條頁根本冇 serif 文字，唔 preload 即係一個字型檔都唔洗載。

5. `next.config.ts` 加 `/fonts/:path*` → `Cache-Control: public, max-age=31536000, immutable`。
   檔名帶內容雜湊（`serif-tc-core-900.<hash>.woff2`），所以可以安全鎖一年。

### 實測結果（本機 production build ＋ 瀏覽器冷載）

| 指標 | 改之前 | 改之後 | 工單方案 B 通過標準 |
|---|---|---|---|
| 字型檔數（首頁） | 31 | **2** | ≤ 4 ✅ |
| 字型位元組（首頁） | 2,167 KB | **126 KB** | ≤ 400 KB ✅ |
| `@font-face` 條數 | 536 | **6** | ≤ 20 ✅ |
| 渲染阻塞 CSS | 3 檔／595 KB 未壓縮／89 KB 壓縮 | **1 檔／94 KB 未壓縮／16 KB 壓縮** | — |
| 首頁總傳輸推算 | ~2,460 KB | **~380 KB** | ≤ 700 KB ✅ |
| 詞條頁字型位元組 | 2,167 KB | **0 KB** | — |

按工單嘅線性外推（慢速 4G ＝ 204.8 KB/s）：380 ÷ 204.8 ≈ **1.9 秒**，
落喺工單方案 B 預估嘅「FCP 2.5–4 秒／效能 85–95」區間之內，甚至好啲。
桌面版同步受惠：渲染阻塞 CSS 由 89 KB 壓縮跌到 16 KB，係桌面 FCP 1.9 秒嗰段嘅主要成本。

### 逐字驗證（唔靠推測）

用 canvas 量度逐個字元喺 `Noto Serif TC Subset` 同 fallback 之下嘅字寬／字高，
確認首頁、文章頁（含朱批大字「許」）、詞條頁所有 serif 算繪字元全部由 subset 出，
對照組罕見字「龘」正確落 fallback。無 console error，手機 375px 無橫向溢出。

### ⚠️ 日後維護（重要）

**改咗任何 `font-serif` 標題文案、或加新嘅 serif UI 文字之後，要重跑 subset**：

```bash
npm run build && py -3 scripts/build_font_subset.py && npm run build
```

（第一次 build 出 HTML 俾 script 掃字表，第二次 build 令新 `fonts.css` 入 bundle。）
之後 commit `public/fonts/`、`src/app/fonts.css`、`src/lib/font-preload.ts`。

唔重跑唔會爆版：新字會由 ext 層或系統宋體頂上，最多係嗰隻字字型稍為唔同。
來源字型 `scripts/.fontcache/NotoSerifTC-VF.otf`（15 MB）已 gitignore，script 會自動下載。

**新文章唔需要重跑**：文章標題同正文都唔行 serif，只有正文第一段第一個字（朱批大字）行 serif，
而 ext 層已經預先收埋全部文章嘅首段首字。

## 二、P2：89 個非文章頁嘅 OG／Twitter 標籤

新增 `src/lib/metadata.ts` 嘅 `buildMetadata()`，一個 helper 套落 14 個檔案，覆蓋全部 89 頁：

```
app/about  app/bazi  app/compat  app/daily  app/consultation  app/latest
app/articles  app/glossary  app/glossary/[term]（→68 頁）
app/categories  app/categories/[category]（→10 頁）
app/privacy  app/terms  app/disclaimer
```

`og:url` 由 `path` 產生，同 `canonical` 用同一個字串，結構上唔可能唔一致。
`og:title` 取「｜」前面嗰截（`og:site_name` 已有站名）。
**description 一律沿用原有文案，冇改寫任何一句。**

驗證：build 出嚟嘅 HTML 逐頁對，13 個靜態頁＋動態 `/articles` 全部 `canonical === og:url`，
`og:title` 逐頁唔同，再冇「命運解決師｜八字命理深度解析」。文章頁 OG 本身正確，冇動過。
