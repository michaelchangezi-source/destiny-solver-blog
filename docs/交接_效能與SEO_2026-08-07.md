## 一、P1 字體瘦身：徹底跳出 next/font（工單方案 A ＋ B 一次做齊）

### 診斷確認

工單量到嘅數字同上一輪本機診斷完全對得上：字體 2,167 KB 佔全站傳輸 88%，
536 條 `@font-face` 塞喺 3 個渲染阻塞 CSS 檔（595 KB 未壓縮／89 KB 壓縮）。
TBT 0 ms、CLS 0，即係話問題純粹係字節數，同 JS 執行同版面無關。

### 做法

1. **內文（Noto Sans TC）整個移除**，改用系統 CJK 堆疊。
   iOS／macOS 落 PingFang TC、Windows 落微軟正黑、Android 本身就係 Noto Sans CJK，
   三邊觀感同原本幾乎一致，但省返 18 個檔／1,123 KB 同 211 條 `@font-face`。

2. **標題（Noto Serif TC）保留，但改自行 subset 自託管**（工單方案 B）。
   新增 `scripts/build_font_subset.py`，用 `fontTools` 由 `NotoSerifTC-VF.otf`
   切出 400／700／900 三個字重嘅精簡 woff2，放 `public/fonts/`，
   `@font-face` 寫喺自動生成嘅 `src/app/fonts.css`。

3. **兩層 subset，解決「日後加新標題會缺字」呢個方案 B 嘅已知風險**：

   | 層 | 字表來源 | 大小 | 幾時下載 |
   |---|---|---|---|
   | core | 掃 `.next` 產生嘅 225 個 HTML，抽所有 `font-serif` 範圍內實際算繪嘅字＋`.prose` 首段首字（朱批大字）＝222 字 | 每字重 ~62 KB | 正常情況只下載呢層 |
   | ext | 安全網：全部文章標題／Markdown 標題／`.tsx` UI 字串＝1,406 字 | 每字重 ~295 KB | `unicode-range` 圈住整個 CJK 區但排喺 core 之前，只有出現 core 冇涵蓋嘅字先會拉，平時零位元組 |

   CSS 後定義者優先，所以 core 有嘅字一定由 core 出，ext 唔會被拉。
   萬一連 ext 都冇（極罕），字型堆疊後面仲有系統宋體兜底，唔會出豆腐方格。

4. `preload` 只落首頁（首頁 LCP 元素＝hero H1，`font-serif font-black`＝900）。
   用 `react-dom` 的 `preload()` 而唔係喺 `<head>` 寫 `<link>`，因為 Next 會將 head 內嘅 link
   再 hoist 一次，會出兩條重複標籤。68 個詞條頁根本冇 serif 文字，唔 preload 即係一個字型檔都唔洗載。

5. `next.config.ts` 加 `/fonts/:path*` → `Cache-Control: public, max-age=31536000, immutable`。
   檔名帶內容雜湊（`serif-tc-core-900.<hash>.woff2`），所以可以安全鎖一年。

### 2026-08-08 回退與修正：core 字表漏咗「每日變動」嘅字

**症狀**：上線第二日 PSI 手機由 90+ 跌返 72，FCP 3.5s／LCP 5.0s。

**PSI 直接指出**：關鍵請求鏈入面出現 `/fonts/serif-tc-ext-900.woff2` **299.50 KB／1,083 毫秒**。
嗰塊 ext 本來設計成平時零下載。

**病因**：core 字表只掃 build 當日嘅 HTML 快照，但首頁 hero 有三格係**每日變**嘅 serif 內容 ——
今日天干（900）、今日地支（700）、今日能量標題（900，`InkFlowHero.tsx` 190 行）。
Build 嗰日啱好係一個組合，第二日變成「木火相生，擴張之日」，「擴」「張」兩隻字唔喺 core，
瀏覽器就為咗**兩隻字**拉咗成塊 299 KB 落嚟，仲要卡喺 LCP 路徑上。
`/daily`、`/bazi`、`/compat` 三頁嘅四柱天干地支同五行條都有同一問題。

**兩層修正**：

1. **core 硬性收入可窮舉嘅動態詞彙**（`collect_dynamic()`）：10 天干＋12 地支＋5 五行＋
   `bazi-daily.ts` 全部 15 個 `energyTitle`，合共 67 字。唔再靠 HTML 快照撞彩。
   core 由 222 字升到 246 字，每字重 62 → 68 KB。
   （script 加咗保險：若 `bazi-daily.ts` 搵唔到任何 `title:` 就直接中止，唔會靜靜哋放行。）
2. **ext 由一整塊切做 10 塊**（每塊約 140 字／22–41 KB）。就算日後真係再漏字，
   代價由 299 KB 降到最多 41 KB，唔會再一隻字拖冧成個分數。
   代價係 CSS 由 16 KB 升到 21 KB（壓縮後），因為 unicode-range 要逐段列明。

**驗證**：核對 15 個 energyTitle ＋ 干支五行喺 core-900／core-700 嘅 cmap 全部涵蓋；
本機 375px 冷載，`ext` 一塊都冇下載，全頁 serif 零字元跌落系統宋體。

## 五、Service Worker：部署後「撳連結冇反應」嘅潛伏 bug（同日已修）

Mic 部署後回報：`/latest` 撳唔入每篇文章。

**先排除咗嘅**（唔係呢啲）：伺服器同程式碼兩邊健康 —— `/latest` 90 條連結齊全、
逐條文章 URL 回 200、本機 production 程式碼喺 desktop（1280px）同 mobile（375px）
模擬點擊都正常導覽入文章頁、無 console error。即係問題喺客戶端快取。

**病因**：舊版 `public/sw.js`（cache 名 `ds-v1`）對「所有同源 GET」一律 cache-first，
包括 HTML 頁面同 Next.js 客戶端路由用嘅 RSC payload。每次部署之後：

1. 瀏覽器繼續由快取攞部署前嘅 HTML ＋ 舊 build ID 嘅 JS chunk
2. 但撳連結嗰陣，Next 客戶端路由要即時攞新 build 嘅 RSC payload
3. 新舊對唔上 → 撳咗冇反應

**呢個係每次部署都會復發嘅潛伏 bug，唔係字型改動引起**，亦好可能係過往幾輪
「改完又出新問題」嘅其中一個真兇。

**修法**（commit `cb0dd43`）：

- cache 名 `ds-v1` → `ds-v2`。`activate` 事件本身就會刪走名唔同嘅舊快取，
  所以訪客載入新 SW 之後，中咗毒嘅 `ds-v1` 會自動清走，唔使人手 unregister
- `/_next/static`、`/fonts`、`/images`（檔名帶內容雜湊）維持 cache-first
- 導覽（HTML）改 network-first，只喺離線先用快取兜底，保留 PWA 離線可用同可安裝性
- RSC payload（`RSC` header 或 `_rsc` query）、`/api` 一律唔攔截

**日後鐵律**：改 `sw.js` 嘅快取策略，一定要順手 bump 一次 cache 名（`ds-v2` → `ds-v3`），
否則舊訪客會一直用緊舊策略同舊內容。

**訪客要做嘅嘢**：冇。新 SW 一到就自動接管兼清快取。急住即刻見到可以硬重新整理
（Ctrl+Shift+R）或開無痕視窗。
